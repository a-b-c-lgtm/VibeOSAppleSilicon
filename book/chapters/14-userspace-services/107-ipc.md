# Chapter 107 — IPC: a tiny message bus for long-running services

**Status:** Stub. Tracking milestone 90a.

So far every cross-process channel we have is
1-to-1 and parent-child shaped: pipes (chapter 39),
shared fd tables (chapter 93), the GUI syscalls
between an app and the in-kernel WM. We have nothing
that lets an *arbitrary* app talk to an *unrelated*
long-running service — and we are about to need one for
the clipboard, then again for the audio mixer, then
again for the future TLS proxy, then again for every
filesystem server (Part XVI).

Rather than ship the clipboard as a kernel feature and
then duplicate the same plumbing for each new service,
this chapter adds the missing primitive: a Unix-shaped
named IPC channel, a service-discovery convention, and
the supervisor work to keep services alive. Every later
"daemon" chapter (clipboard, audio mixer, /bin/httpd,
9P-shaped filesystem servers) will sit on top of these
three things.

## What this chapter adds

- **`/srv/<name>` namespace.** A new node kind in the
  VFS (`FD_SRV_LISTEN` / `FD_SRV_CONN`) — not backed by
  a filesystem, just a kernel-side table of advertised
  service endpoints keyed by path.
- **`SYS_SRV_BIND(path)`** — a service calls this once
  at startup; the kernel registers the calling thread as
  the listener for `path`. Returns a listening fd.
- **`SYS_SRV_ACCEPT(listen_fd)`** — blocks until a
  client connects; returns a connected fd. Shape mirrors
  `SYS_SOCKET_ACCEPT` from chapter 104, so an app that
  knows how to write a TCP server already knows how to
  write an IPC service.
- **`SYS_SRV_CONNECT(path)`** — a client opens
  `/srv/<name>` and gets back a connected fd. Equivalent
  in effect to `connect(AF_UNIX, ...)`.
- **Message framing.** Read/write on a connected fd
  delivers length-prefixed datagrams (not a byte stream),
  capped at 64 KiB per message. This makes clipboards,
  RPCs, and config blobs trivial to send; streaming
  larger blobs is still possible by chunking.
- **Supervisor.** `init` learns to spawn entries from
  `/etc/services.conf` (or a baked-in default list)
  and respawn them on crash. The same machinery the
  desktop already uses for auto-spawn, generalised.

## Design decisions

### Path-named, not number-named

`SYS_SRV_BIND("/srv/clipboard")` instead of
`SYS_SRV_BIND(SRV_CLIPBOARD)`. Names mean the kernel
doesn't grow a registry of "well-known service IDs"
that we'd have to allocate forever. Adding a new
service is `bind("/srv/whatever")` — no kernel change.

### Datagram, not stream

Pipes are byte streams; sockets are byte streams. For
RPC-shaped traffic that's almost always a mistake: every
caller has to invent its own length prefix or delimiter.
We make the framing the kernel's job: every `write` is
one message, every `read` returns exactly one message (or
`EMSGSIZE` if the caller's buffer is too small).

### One thread per service is the v1 contract

Real Unix has `accept` → `fork` per connection. We're
not there yet — `accept` returns the connected fd and
the service can either handle it inline (clipboard:
trivial, sub-millisecond) or spawn a worker thread via
`clone` (chapter 91). The kernel doesn't fork on the
service's behalf.

### Service supervision is `init`'s job, not the kernel's

The kernel exposes the namespace and the framing; the
"keep the daemon alive" policy lives entirely in
userspace. This matches how chapter 17's `init` already
spawns the initial process tree, and lets us evolve the
supervision rules (restart with backoff, dependency
ordering, log rotation) without ABI changes.

### Authentication: deferred

For v1 every client can connect to every service.
We have no user/group model yet, so adding capability
checks would be premature. Future: a per-bind allow
list of pids or a `SO_PEERCRED`-shaped query.

## Plan

1. Add `FD_SRV_LISTEN` and `FD_SRV_CONN` fd kinds
   beside `FD_PIPE` and `FD_SOCKET`.
2. Implement the three syscalls; the listen object is
   a small struct with a waiter queue and a pending-
   connection queue.
3. Add the `/srv` prefix to VFS dispatch so
   `open("/srv/clipboard", O_RDWR)` becomes
   `SYS_SRV_CONNECT("clipboard")` internally — apps
   that don't know about IPC can still talk to services
   through `read`/`write`/`close`.
4. Extend `init` to read `/etc/services.conf` and
   spawn-and-supervise each entry.
5. Write `/bin/srvls` (lists `/srv/*`) and `/bin/srvtest`
   (round-trips one message) as smoke tests.
6. Regression test (`scripts/test_ipc.py`): spawn
   srvtest as a service, have a second client send a
   message, assert the echo.

## What you'll learn

- Why every mature Unix has *some* shape of named-IPC
  socket (X11 selections, D-Bus, Mach ports, Wayland's
  `wl_display`) — and why "we'll just use files" is
  the answer everyone tries first and abandons second.
- The framing-in-the-kernel vs framing-in-the-app
  trade-off, settled definitively for our toolkit.
- A supervisor pattern that scales from "restart this
  daemon" to "honour a dependency graph" without
  changing the IPC ABI.

## What this unlocks

- **Chapter 108 — clipboard as a userspace service.**
  `/bin/clipboardd` binds `/srv/clipboard`, handles
  `set`/`get`/`generation` over IPC. Three syscalls
  *don't* go into the kernel.
- An audio mixer daemon (`/bin/mixer`) that arbitrates
  virtio-snd across multiple apps without putting
  mixing in the kernel.
- A future TLS termination proxy as a userspace
  service the browser opens via `/srv/tls`.
- The 9P-shaped filesystem servers from chapter 114.
- A clean place to add per-user permissions later,
  without retrofitting them into N independent
  kernel surfaces.
