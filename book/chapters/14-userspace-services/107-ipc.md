# Chapter 107 — IPC: a tiny message bus for long-running services

> **Milestone in this chapter:** 80b — named IPC + `/srv/<name>`.
> **Code referenced:**
> - [kernel/core/srv.c](../../../kernel/core/srv.c)
> - [kernel/core/syscall.c](../../../kernel/core/syscall.c)
>   (`SYS_SRV_BIND`, `SYS_SRV_CONNECT`, `SYS_SRV_ACCEPT`)
> - [kernel/core/vfs.c](../../../kernel/core/vfs.c) (the `/srv/`
>   prefix dispatch)
>
> **At the end of this chapter** you will have three new syscalls
> and one new VFS prefix that let an arbitrary process talk to an
> unrelated long-running service through a path of the form
> `/srv/<name>`. Every later daemon chapter (clipboard, audio mixer,
> the in-guest httpd, the 9P-shaped filesystem servers in Part XVI)
> sits on top of this primitive.

Every cross-process channel so far has been 1-to-1 and parent-child
shaped: pipes (chapter 39), shared fd tables (chapter 93), the GUI
syscalls between an app and the in-kernel WM. Nothing in the system
yet lets an *arbitrary* app talk to an *unrelated* long-running
service — and the clipboard chapter is about to need exactly that,
then again for the audio mixer, then again for the future TLS
proxy, then again for every filesystem server (Part XVI).

Rather than ship the clipboard as a kernel feature and then
duplicate the same plumbing for each new service, this chapter adds
the missing primitive: a Unix-shaped named IPC channel keyed by a
`/srv/<name>` path.

## What this chapter adds

- **`/srv/<name>` namespace.** A new node kind in the
  VFS (`FD_SRV_LISTEN` / `FD_SRV_CONN`) — not backed by
  a filesystem, just a kernel-side table of advertised
  service endpoints keyed by path. Lives next to
  `/proc` in the "pseudo-namespace surfaced through
  VFS" register.
- **`SYS_SRV_BIND(path)`** — a service calls this once
  at startup; the kernel registers the calling thread
  as the listener for `path`. Returns a listening fd.
- **`SYS_SRV_ACCEPT(listen_fd)`** — blocks until a
  client connects; returns a connected fd. Shape
  mirrors `SYS_SOCKET_ACCEPT` from chapter 104, so an
  app that knows how to write a TCP server already
  knows how to write an IPC service.
- **`SYS_SRV_CONNECT(path)`** — a client opens
  `/srv/<name>` and gets back a connected fd.
  Equivalent in effect to `connect(AF_UNIX, ...)`. The
  VFS `/srv/` prefix routes `open("/srv/foo", O_RDWR)`
  through this same path so clients that don't know
  about IPC can still talk to services with plain
  `read`/`write`/`close`.
- **Message framing.** Read/write on a connected fd
  delivers length-prefixed datagrams (not a byte stream),
  capped at 64 KiB per message (`SRV_MSG_MAX`). Each
  `read` returns exactly one message; each `write`
  enqueues exactly one. `-EMSGSIZE` is returned (and
  the message stays queued) if the caller's read
  buffer is too small.

The supervisor work — having `init` read
`/etc/services.conf` and respawn crashed services on
backoff — is folded into chapter 108 (the first real
client of the bus). Without an actual service to
supervise, the supervisor would be untestable in this
chapter.

## Design decisions

### Path-named, not number-named

`SYS_SRV_BIND("/srv/clipboard")` instead of
`SYS_SRV_BIND(SRV_CLIPBOARD)`. Names mean the kernel
doesn't grow a registry of "well-known service IDs"
that we'd have to allocate forever. Adding a new
service is `bind("/srv/whatever")` — no kernel change.

### Datagram, not stream

Pipes are byte streams; sockets are byte streams. For
RPC-shaped traffic that's almost always a mistake: every
caller has to invent its own length prefix or delimiter.
We make the framing the kernel's job: every `write` is
one message, every `read` returns exactly one message (or
`EMSGSIZE` if the caller's buffer is too small).

Implementation-wise the per-direction queue stores one
heap-allocated `struct srv_msg { len; data[] }` per
in-flight message. Not a fixed ring with `SRV_MSG_MAX`
slots — that would pre-allocate 64 KiB per slot whether
the messages were 16 bytes or 16 KiB. Per-message heap
pays the cost only for the bytes actually in flight.

### One thread per service is the v1 contract

Real Unix has `accept` → `fork` per connection. We're
not there yet — `accept` returns the connected fd and
the service can either handle it inline (clipboard:
trivial, sub-millisecond) or spawn a worker thread via
`clone` (chapter 91). The kernel doesn't fork on the
service's behalf.

### Service supervision is `init`'s job, not the kernel's

The kernel exposes the namespace and the framing; the
"keep the daemon alive" policy lives entirely in
userspace. This matches how chapter 17's `init` already
spawns the initial process tree, and lets us evolve the
supervision rules (restart with backoff, dependency
ordering, log rotation) without ABI changes. Chapter 108
is where the supervisor actually shows up, paired with
the first real service that needs supervising.

### Authentication: deferred

For v1 every client can connect to every service.
We have no user/group model yet, so adding capability
checks would be premature. The `struct srv_listen`
already carries `owner_pid`, and the `struct srv_conn`
records both `peer_pid_c` and `peer_pid_s`, so a future
chapter can add a per-bind allow list or a
`SO_PEERCRED`-shaped query without ABI changes.

### Listener fds are not inherited across fork

`FD_SRV_LISTEN` is treated by `fork()` exactly like
`FD_SOCKET_LISTEN`: not inherited, because the kernel
registry is single-owner and an inherited listener
would let the child accept on the parent's name. The
same opt-out covers `FD_SRV_CONN` for v1 — the
connection-side refcount machinery would need the same
careful TCP-cid treatment, and that pays for itself
only once someone needs to share an in-flight conn
across fork. Defer.

## Walkthrough

The three syscalls are about as small as they get. Here
is `sys_srv_bind`:

```c
static long sys_srv_bind(long path_uptr)
{
    char path[SRV_NAME_MAX];
    long r = copy_path_from_user(path, sizeof(path), path_uptr);
    if (r < 0) return r;
    int err = 0;
    struct srv_listen *ls = srv_bind(path, &err);
    if (!ls) return err ? err : -ENOMEM_VFS;
    int fd = vfs_alloc_srv_listen_fd(ls);
    if (fd < 0) {
        srv_unref_listen(ls);
        return fd;
    }
    return fd;
}
```

`srv_bind` validates the path (must start with `/srv/`,
no further `/`, fits in `SRV_NAME_MAX`), checks the
registry for a duplicate (`-EADDRINUSE`), and takes the
first free slot in a fixed `g_listeners[16]` array. The
fd allocator follows the chapter-104 `vfs_alloc_listen_fd`
template line-for-line.

`sys_srv_accept` is even shorter — `srv_accept` does the
real work in a `thread_block_on(ls)` loop that drains
the listener's pending-connection queue. The pre-eret
`sig_pending` check (chapter 79b) lets a Ctrl-C kill an
accept-camped service in finite time.

`sys_srv_connect` mirrors it: allocate a `struct srv_conn`
with both directions empty, enqueue a `struct srv_pending`
on the target listener, wake the listener, then block on
the conn until the service flips `service_open = 1`. If
the service has gone away mid-handshake we surface
`-EPIPE`; if the caller got a signal we walk back over
the pending queue to revoke the half-open conn and
return `-EINTR`.

The read path is one heap-allocated buffer per message,
which is also the unit of framing — `srv_read` either
returns exactly one message's bytes or `-EMSGSIZE` if
the caller's buffer is too small (the message stays
queued for the next call). `srv_write` mirrors it: one
`kmalloc(sizeof(srv_msg) + len)`, push to the right
direction's queue, wake the reader.

Both ends share the conn via a refcount-shaped pair of
flags (`client_open`, `service_open`); the unref helper
flips its own flag, wakes the peer, and `kfree`s the
conn when both flags are clear.

## Tests

`scripts/test_ipc.py` is the chapter capstone — entirely
hermetic, no host networking. It boots the kernel, drops
to the shell prompt, and runs `srvtest`. The userspace
`srvtest` forks once:

- **Parent (service):** `srv_bind("/srv/echotest")`,
  `srv_accept()`, `read()` one message, `write()` it
  back, `close()`.
- **Child (client):** `srv_connect("/srv/echotest")`,
  `write("ipc-hello\n")`, `read()` the echo, `close()`.

The test asserts seven serial-log markers: bound,
connected, accepted, message received (10 bytes intact),
echo received intact, done line, clean exit. End-to-end
under 5 seconds.

The test exercises every new code path:

- `SYS_SRV_BIND` → path validation + registry insert.
- `SYS_SRV_ACCEPT` → block / wake handshake with
  `srv_connect`.
- `SYS_SRV_CONNECT` → pending-queue plumbing + the
  `service_open` rendezvous flag.
- `FD_SRV_CONN` read/write → length-prefixed datagram
  framing in both directions (`c2s` and `s2c`).
- `vfs_close` routing for `FD_SRV_LISTEN` +
  `FD_SRV_CONN` — refcount-driven free, no leaks.
- `fork()`'s per-kind FD inheritance skip for
  `FD_SRV_LISTEN` (added beside the chapter-104 skip
  for `FD_SOCKET_LISTEN`).

## Postscript — IPC resiliency under GUI resize storms

Follow-up debugging in May 2026 surfaced an important
runtime detail for chapter-107 clients: even though the
IPC transport is datagram-framed, `read`/`write` on a
`FD_SRV_CONN` can still return transient scheduler/signal
errors like `-EINTR` (`-4`) or `-EAGAIN` (`-11`).

This is exactly what happened on `/srv/wm` during rapid
browser resize: `wmclient` saw `[wmclient] read err n=-4`,
poisoned its cached conn, and then resize remap requests
started failing in a loop.

The fix pattern is now the recommended chapter-107 client
discipline:

1. Retry `read`/`write` on `-EINTR`/`-EAGAIN`.
2. Only treat hard errors (`-EPIPE`, short/failed I/O,
   dead peer) as a poisoned connection.
3. Reconnect lazily on the next operation that needs the
   channel.

`wmclient` in
[userspace/libgui/wmclient.c](../../../userspace/libgui/wmclient.c)
implements exactly that policy now. The underlying chapter-107
transport did not change; the resiliency fix is in client
error-handling.

## What this unlocks

- **Chapter 108 — clipboard as a userspace service.**
  `/bin/clipboardd` binds `/srv/clipboard`, handles
  `set`/`get`/`generation` over IPC. Three syscalls
  *don't* go into the kernel. Also where the
  `init`-side supervisor (`/etc/services.conf` reader
  + respawn-on-crash loop) lands, now that there's an
  actual service to supervise.

  mixing in the kernel.
- A future TLS termination proxy as a userspace
  service the browser opens via `/srv/tls`.

  without retrofitting them into N independent
  kernel surfaces.
