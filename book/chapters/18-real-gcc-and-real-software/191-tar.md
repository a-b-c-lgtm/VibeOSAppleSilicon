## Why now

By the end of chapter 190 the toolchain story for in-guest C
development looked like this:

| Tiny smoke programs (hello.c, bf.c, stdio_test.c) | ✅ | 188 |
| **A way to put 200 source files on `/data/`** | ❌ | — |

That last line is the gap. DoomGeneric ships as ~62 K lines of
C in 202 source files (no nested subdirs, but plenty of them).
`/bin/gcc` can compile them one at a time, `/bin/make` can
drive the loop, but neither has any way to *carry* a 200-file
tree across the host/guest boundary.

Three obvious choices:

### Option A — bake each file into OSFS-1 individually

OSFS-1's flat 256-entry dirent table is *just* big enough; the
20-byte name field handles `r_main.c` style names easily, and
the chapter-190 trick (literal `/` in name field) handles
nested `dehacked/` directories if a future chapter needs them.
After 190 the image holds 163 entries; adding 202 file entries
would push it to 365 — over cap. Even if the cap got raised,
build-system structure would be encoded into the filesystem
image, and the in-guest `make` would have to fish each file out
of `/bin/` where it doesn't belong.

### Option B — implement gzip and ship a `.tar.gz`

This is what every distro does. It's also ~3000 lines of
inflate code (`vendor/zlib/inflate.c` style) before the
archive reader starts. That's a lot of code to own from day
one for a tarball this build pipeline controls end-to-end at
build time — compression buys nothing.

### Option C — ship a plain ustar tarball + read it in-guest

A ustar header is 512 bytes of fixed-offset ASCII fields. A
read-only ustar parser is ~200 LoC. The host-side producer is
under full control here, so it can be guaranteed to use no
GNU long-name extensions, no PAX records, no symlinks — the
simplest possible dialect.

This chapter implements option C.

## What `/bin/tar` supports

```text
tar tf <archive>            # list
tar xf <archive> [-C dir]   # extract (default cwd)
```

That's it. No create mode (not needed in-guest), no update,
no `--gzip`, no `--bzip2`. The argv parser rejects everything
else.

Two typeflags are honoured:

* `'0'` (or `'\0'` from old tars) — regular file
* `'5'` — directory

Symlinks, hardlinks, character/block devices, FIFOs, and the
`L` / `K` GNU long-name extensions are printed with
`"tar: skipping <name> (typeflag 'X' not supported)"` and
their body is correctly skipped. DoomGeneric's tree has none
of them, so this path never fires in practice.

## Pitfalls

### Pitfall — end-of-archive is *two* zero blocks, not one

**Symptom:** A reader that bails on the first all-zero 512-byte
block truncates archives whose creators padded between members
with a single zero block (some old `tar`s did this).

**Cause:** The ustar spec ends an archive with at least two
consecutive zero-filled 512-byte blocks. A single zero block
in the middle of an archive is technically legal.

**Fix:** Count the run and only stop at the second:

```c
if (is_zero_block(block)) {
    zero_run++;
    if (zero_run >= 2) break;   /* clean EOA */
    continue;
}
zero_run = 0;
```

On the very first iteration this happens to also catch a
zero-length archive cleanly.

### Pitfall — `'\0'` is the *same* typeflag as `'0'`

**Symptom:** Regular files written by old `tar` implementations
parse as "unknown typeflag" and get skipped on extract.

**Cause:** Old `tar` left the typeflag byte as NUL for regular
files. POSIX added `'0'` later. Both have to be treated
identically.

**Fix:** Normalise up front:

```c
char tf = h->typeflag;
if (tf == 0) tf = '0';
```

### Pitfall — skip the body even in list mode

**Symptom:** `tar tf` against a multi-file archive thinks file 17
has a 0o7777777777777-byte size and aborts with "malformed size
field".

**Cause:** A header is *always* followed by
`ceil(size/512) * 512` bytes of data (zero-padded for the last
block). Even when listing (no extraction), the reader has to
advance past those bytes to find the next header. Forgetting
the pad makes the next read land mid-file and parse random
bytes as a header.

**Fix:** Always advance by the full padded size:

```c
long total = sz + ((BLOCK - (sz % BLOCK)) % BLOCK);
while (total > 0) {
    char skipbuf[BLOCK];
    long want = total > BLOCK ? BLOCK : total;
    if (read_n(fd, skipbuf, want) < 0) return -1;
    total -= want;
}
```

### Pitfall — no `mkdir -p` in the on-disk libc

**Symptom:** Extracting a multi-component path like
`src/dehacked/foo.c` fails with `ENOENT` because the libc has
no recursive directory-create.

**Cause:** OSFS-2's `SYS_MKDIR` creates exactly one directory,
returns `-EEXIST` if it's already there, and `-ENOENT` if the
parent is missing. There is no recursive-create.

**Fix:** Walk the path prefix-by-prefix, `mkdir`ing each
component and swallowing `EEXIST`:

```c
static void mkdir_p(const char *path, int with_basename) {
    char buf[512];
    int  len = 0;
    while (path[len] && len < (int)sizeof(buf) - 1) {
        buf[len] = path[len]; len++;
    }
    buf[len] = 0;
    for (int i = 0; i < len; i++) {
        if (buf[i] == '/' && i > 0) {
            buf[i] = 0;
            if (mkdir(buf, 0755) < 0 && errno != EEXIST) {
                /* swallow */
            }
            buf[i] = '/';
        }
    }
    if (with_basename && len > 0 && buf[len - 1] != '/')
        mkdir(buf, 0755);
}
```

`with_basename=0` is used for regular files (parent dir but
not a directory at the file's spot); `with_basename=1` is
used for type-`'5'` entries.

The `EEXIST` swallow is what makes re-running `tar xf` over an
existing tree idempotent — every directory exists from the
first run, so every `mkdir` returns `EEXIST` on the second
run, and extraction keeps going.

## Host-side: `scripts/mktar.py`

Shelling out to `tar` on the host won't work portably: macOS
ships BSD tar by default and Linux ships GNU tar; their
pax-vs-ustar behaviours differ, and the build wants
bit-identical archives across hosts. Python's `tarfile`
module exposes `format=tarfile.USTAR_FORMAT` explicitly:

```python
with tarfile.open(out, "w", format=tarfile.USTAR_FORMAT) as t:
    entries = sorted(src.rglob("*"))           # stable order
    root = tarfile.TarInfo(name=name)
    root.type = tarfile.DIRTYPE
    root.mode = 0o755; root.mtime = 0
    root.uid = 0; root.gid = 0
    root.uname = ""; root.gname = ""
    t.addfile(root)
    for p in entries:
        info = t.gettarinfo(p, arcname=f"{name}/{p.relative_to(src).as_posix()}")
        info.mtime = 0
        info.uid = 0; info.gid = 0
        info.uname = ""; info.gname = ""
        ...
```

Normalising mtime / uid / gid / uname / gname to fixed values
makes the archive byte-identical across rebuilds. That's
useful for `git status` cleanliness if the archive ever gets
checked into the tree.

`sorted(src.rglob("*"))` matters too: APFS, ext4, and HFS+
return inodes in different orders, and unsorted `rglob`
inherits that. With sorting, two macOS developers + one Linux
CI machine all produce the same bytes.

## Why the tarball ships on `/bin`, not `/data`

`/data` is the *writable* filesystem (OSFS-2, 64 MiB). Baking
a 1.9 MB read-only blob into it at format time would mean
teaching `mkosfs2.py` to embed files, making the journal
fsck-tolerate pre-populated inodes, and — worst — the in-guest
`tar xf` would overwrite its own source. Shipping the tarball
on `/bin` (OSFS-1, RO, 256 MiB image) makes it bit-stable
across boots and obvious where it came from.
